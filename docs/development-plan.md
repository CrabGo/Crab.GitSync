# Crab.GitSync 开发计划与任务执行安排

制定日期：2026-10-09。代码基线：v0.4.2。

版本号为规划建议，实际发布前按完成范围确定。以验收结果推进里程碑，不预设未经评估的完成日期；任务进度见下表和执行记录。

## 目标与当前基线

下一阶段先解决连接失败难定位、批量失败需要重复操作、同步状态容易误解、拉取可能产生意外合并提交四个问题。

当前已具备目录扫描、路径历史、批量 fetch、手动合并及撤销、代理配置、任务日志、托盘通知和发布更新。需保留以下行为：

- 批量获取及右键「拉取」只执行 fetch，不修改 HEAD 或工作区。
- 合并、拉取并合并、撤销本地修改和中止合并继续要求明确确认。
- 撤销修改保留新增及未跟踪文件，合并冲突保留现场。
- 应用代理不写入系统或仓库的持久 Git 配置。
- 更新器每进程只初始化一次，更新文件必须通过 SHA256 校验。

当前任务顺序执行，日志仅在内存保留最多 500 条，仓库状态没有成功获取时间，更新页未直接展示正式 ChangeLog。这些是后续工作的明确起点。

### M1 的实现约定

**错误和任务结果**

- 建议错误字段：类别、失败阶段、可否重试、用户提示、脱敏详情。先依据进程退出、上下文取消/超时和 HTTP 状态判断，再用有限的 Git stderr 特征辅助分类；不得将所有错误都当成网络错误。
- 建议任务字段：任务 ID、类型、仓库路径、分支、阶段、尝试次数、开始/结束时间、耗时、结果、错误类别、配置来源。HTTP 代理地址不保存凭据。
- fetch 成功但本地信息刷新失败应分别记录。重试这种结果时优先重新读取本地状态，避免无必要地再次获取远端。
- `fetch --all` 可能部分远端成功：整体失败时不宣称所有远端都是最新，也不清除已经成功获取的引用。

**连接诊断**

- 分为代理地址可连接、GitHub HTTPS 可访问、指定仓库可读取三步；每一步单独计时和返回结果。端口可连不能直接判定代理协议正确。
- 使用只读 HTTP 请求及 `git ls-remote`，不通过 fetch 测试用户仓库。
- 代理关闭时显示实际连接策略；SSH 仓库清楚标注沿用 SSH 配置，不把 HTTP 代理测试结果当成 SSH 认证成功。
- 每步设置超时，整体可取消。诊断并发上限为 1，不阻塞界面，不需要取消正在运行的仓库任务。

**同步状态**

- 提交关系、工作区修改、正在进行的 Git 操作、上次任务结果分别表达，不让单个标签覆盖重要状态。
- 本地有提交且存在跟踪分支时，领先/落后均为 0 → 已同步；仅领先 → 仅本地领先；仅落后 → 仅远端领先；两者均大于 0 → 双方分叉。
- 无跟踪分支、空仓库、分离 HEAD、引用读取失败按各自情况展示，不能默认归入已同步。
- 扫描只读取本地信息，不产生“刚刚成功获取”的时间。M1 的获取时间只保证当前会话有效；跨重启记录由 P12 实现。

**安全拉取**

- 右键「拉取」保持 fetch；「拉取并合并」默认仅快进。普通合并继续保留为明确的手动策略，不自动改用 rebase 或 force。
- 预览基于指定源/目标引用，执行前重新校验。fetch 后提交关系可能变化：重新计算关系，默认仅快进无法完成时停下；不得根据过期确认悄悄生成合并提交。
- 普通合并生成冲突后保留现场，继续提供中止合并。安全检查失败时显示具体原因。
- 不自动 stash、不自动丢弃修改，不自动清理未跟踪文件。

## 执行顺序与工作方式

首个开发任务为 P01，然后按如下顺序推进：

1. P01：先建立错误/任务结果模型，统一 fetch、刷新、更新及操作失败的表达。
2. P02 → P03 → P04：依次完成代理诊断、手动失败重试、可选自动重试；每项独立验证和提交。
3. P05 → P06：完成状态表达，再实现默认仅快进与提交关系确认。
4. P07 → P08：集成验收，修复回归，写准确的发布说明后发布 M1。
5. P09 → P10 → P11 → P12 → P13：交付 M2，先做调度与互斥再开放并发。
6. P14 → P15 → P16：交付 M3，通过共用调度器完成后台获取与后续体验完善。

执行时每次聚焦一个任务，记录变更、测试证据和剩余限制。任务状态使用「待执行 → 进行中 → 待验收 → 完成」；验收未通过不能记为完成。前置任务未完成时，后续任务可准备设计，但不交付依赖未稳定的实现。

每个任务至少包含：

- 明确涉及的模块与兼容性影响；新增 API 后重新生成绑定，不手改生成文件。
- 后端功能实现及有意义的回归场景。
- 实际界面检查，包括错误、空状态、取消、按钮禁用与状态刷新。
- 更新本文任务状态与证据记录。任务状态不替代 Release 验证结果。

## 验证与发布门槛

### M1 必须覆盖的场景

- 代理端口关闭、协议不匹配、GitHub 超时、认证失败、未知错误、正常连接和主动取消。
- 混合成功/失败/无远端仓库；只重试失败项；重试等待时取消；网络错误与本地刷新失败区分。
- 已同步、领先、落后、分叉、无跟踪分支、空仓库、分离 HEAD、冲突及本地有修改。
- 快进成功、分叉拒绝、普通合并确认、合并冲突保留、中止合并、执行前外部切换分支。
- 连续检查应用更新、失败后再次检查、保存代理后新请求生效。
- 批量 fetch 及右键拉取前后 HEAD、工作区内容保持不变。

### 测试隔离

Git 写操作测试只在 `t.TempDir()` 创建的临时仓库中执行。代理与更新自动化测试使用本地 HTTP/代理测试服务及临时配置目录。不得修改开发者或用户仓库，不使用真实凭据，不对开发者正在运行的应用调用 Restart。

### 每次功能发布

1. 前端 `npm ci`、`npm run build`；Go `go test ./...`、`go vet ./...`；`wails3 build`。
2. 新增并发、共享状态或调度时执行相关竞态检查。
3. 完成真实运行界面的验收，区分浏览器预览、原生窗口/托盘和实际更新替换的验证范围。
4. 填写 `releases/vX.Y.Z.md` 的新增、修改、删除、优化；无变化的栏目写「无」。
5. 使用 `build/release.ps1` 构建并校验；确认提交内容和版本一致后推送新标签。
6. 等待线上构建与发布成功，核对正式说明、EXE、SHA256SUMS；验证匿名检查、下载与哈希。

真实更新替换、恢复与重启测试使用独立测试安装目录和可关闭的测试实例，不操作开发者主应用；没有完成的验证必须如实记录。

## 延后范围

GitHub 登录、push、rebase、强制同步、内置冲突编辑器、跨平台发布及安装包签名暂不纳入上述三个里程碑。后续根据实际使用反馈单独拆分，避免影响优先任务交付。
